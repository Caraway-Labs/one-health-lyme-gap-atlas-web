# County review methodology v1

Status: Canonical initial methodology and configuration contract, 2026-10-05. Owner: Web #249. Rule activation remains governed by the explicit gates below. This is the normative method specification for API #93, not an implemented API result or a public disease claim. The existing Atlas score and Data #172 surveillance triage are different methods. Web #455 is a **post-deployment** settings/product review, not a delivery dependency for #249, API #93 or Web #411.

## Identity and boundary

Approved ID and first version: `atlas-county-review@1.0.0`. Every authoritative result carries `methodology_id`, `methodology_version`, immutable Git config commit/hash, data release/version, evaluation/as-of time, requested state and observation context, and each cited evidence item's source, publisher/version, geography, observation interval, source availability/revision and retrieval time, value/evidence state, method/era, quality/effort, and limitations. A **major** version materially changes candidate meaning, eligibility, result states, or reason interpretation; a **minor** version adds a backward-compatible approved family, candidate reason, or enabled rule; a **patch** corrects behavior/documentation without changing intended scientific/product semantics. A parameter change that can alter candidate decisions requires a new minor version and fixture replay. Pin result reproduction to code revision, config hash, source release, and input snapshot; Git hash alone does not reproduce mutable source data.

Invariant code owns state precedence, eligible families, absence/unknown semantics, safety claims, and reason taxonomy. Reviewed Git configuration owns rule enablement, eligible sources and source-specific tunable parameters. The initial Git artifact is [`county-review-methodology-v1.config.json`](county-review-methodology-v1.config.json); API #93 owns its validated loader and deployed pinned copy. Snowflake owns governed observations and reference identities. API #93 executes the typed method; Web #411 consumes the result. An optional registry may select an approved version, never supply executable expressions. Later #455 changes to decision meaning or parameters require the appropriate new methodology/configuration version and fixture replay.

## API #54 and historical-evidence reconciliation

Closed API #54 implements `GET /v1/observations` with bounded measure, county FIPS, year/date and pagination filters. Its route explicitly says **current published county observations only**. The governed current-release projection contains only `human_status`, `case_count_floor_2023`, and `incidence_floor_2023`, each with a single 2023 county period and no supported strata. A 2024 query returns an empty collection. The accepted #54 "time-series" criterion was explicitly satisfied under an owner-approved **single-period interpretation**; the endpoint is technically time-filterable, not a live multi-year series. The human count is a published privacy-protected **floor**, the incidence is derived from that floor and current SVI/ACS population context, and `NO_COUNTY_LINKED_RECORD` is not zero. Neither vector nor pathogen observation is exposed through this #54 projection. The older county summary API carries current/cumulative vector/pathogen status labels; they are not annual observations or sampled negatives.

Data #110 separately inventoried approved DEV conformed CDC county-of-residence annual report-year rows: `qtbi-xd4i` (2008–2021) and `x5j9-wybp` (2022–2023), 7,681 distinct _published_ county-year keys across 840 counties in its 2026-09-28 read-only audit. Those are source/DEV inventory evidence, not public #54 results, a complete county-year panel, exact case totals, or proven historical-as-of rows. The published demographic sums and 2023 release are floors; absent county-years, suppressed county IDs and state-unallocated cases cannot be zero-filled or allocated. The inventory found no proven exact mature county-year labels or annual historical population denominators. Data #430's era contract is merged; #431's temporal-alignment contract is merged. Their existence does not prove a particular pair of observations comparable, nor that the public API projects the metadata. Data #111 owns bounded source qualification/acquisition gaps; #110 owns portfolio/evidence inventory, and #113 owns **ML forecast-cutoff** panel proof. That strict forecasting as-of requirement is not automatically a retrospective county-review requirement; review still needs source version, revision, observation and availability dates disclosed.

The immediate split is **data/semantic representation plus methodology approval**, with API propagation for a live review engine: historical rows exist in DEV but candidate-quality within-county changes are not proven from floor values or missing years, and the current published API release exposes one period. No new source acquisition is automatically required. API #93 can consume a reviewed governed historical projection/adapter if one becomes eligible; API #88 owns propagation of Data #428 evidence-state/era/alignment semantics. Data #429 remains open for vector/pathogen domain states. Do not open a duplicate ticket before #110/#111 source findings and the API #93/#88 adapter design show a genuinely unowned outcome.

## Evaluation order and outputs

Evaluate the requested state and each canonical county against the same pinned release. Preserve unsupported input family and missing-data diagnostics even when another supported rule succeeds.

1. Validate county/state identity, source eligibility, exact construct, provenance, release and observation period. Unknown source semantics, ambiguous geography/revision, unsupported domain states, and unsafe comparison produce no comparison-based candidate. Emit a limitation or abstention reason.
2. Recognize observed positive human or county-native vector/pathogen evidence only from a governed positive source state. A published count floor is positive only when it actually proves `>0`; suppression, absent record and unknown remain unknown. A `No records` tick label is not a negative. Context or missingness alone cannot satisfy this gate.
3. For each enabled rule, require its necessary observation intervals, source availability, method/era comparability, required denominator/effort, freshness and source-specific eligibility. A cross-era `CAUTION_REQUIRED` result is visible as caution but is not silently approved for comparison; `UNSUPPORTED`/`UNKNOWN` abstain. A cumulative status cannot be treated as annual incidence. A site/event cannot be generalized to a county.
4. Evaluate emerging change only within a comparable human series or a separately approved county-native vector/pathogen temporal series. Evaluate discordance only where the two constructs have aligned scope and supported semantics. Each positive candidate needs a traceable observed signal and a rule-specific materiality decision. No forced top N, weighted composite, or risk score.
5. Emit per-county completeness independent of concordance. `sufficient` means all evidence required by the evaluated rule is present and eligible; `limited` means the result remains interpretable with stated caveats; `insufficient` means the rule cannot be evaluated. These labels are method-specific, not a claim that all surveillance in a county is complete. Map to UI `Available` / `Limited` / `Unavailable` without erasing detailed reasons.

County outputs are `candidate`, `none_stand_out`, `insufficient_evidence`, or `unsupported`; data gaps are a separate collection and may coexist with a candidate. State aggregation precedence: one or more supported candidates => `candidates_found`; otherwise, if at least one **enabled supported** rule cannot be evaluated for the requested scope => `insufficient_evidence`; otherwise, if no requested rule is enabled/supported => `unsupported`; otherwise => `none_stand_out`. `none_stand_out` requires that at least one approved rule actually ran on eligible evidence across its declared assessed universe; it does not mean no Lyme activity. A disabled rule is never counted as a negative result. Data-gap-only counties never become candidates; gaps that block an enabled rule yield `insufficient_evidence`, while an entirely disabled rule set yields `unsupported` with separate gaps. A candidate does not suppress other counties' abstentions. API must report assessed/eligible/abstained county counts and rule coverage, so a state with one candidate does not hide incomplete surveillance.

## Rule shapes

Rules A, B and C are **defined but disabled in initial `1.0.0`** because their evidence/comparison gates are not satisfied. Rule D is defined as the first bounded current-state evidence-inspection reason and is **prepared for API #93 implementation**, with its enabled flag initially false until the source-use/provenance gates are verified. Disabled rules emit no candidate reason; return rule-level unsupported/insufficient coverage and the precise abstention/data-gap reasons rather than silently reporting `none_stand_out`. Activation or a changed tunable value that affects decisions requires a reviewed new methodology/configuration version, source-backed fixtures and an immutable config hash. Delivery of the engine and Review UI does not wait for Web #455.

**Emerging human contract:** inputs are source-native annual county-of-residence human observations, exact source/product/version and case construct, county boundary, report year, value and censoring/floor state, observation and source revision/availability time, and Data #430 era/comparison result. Compare a current eligible county period with an approved **within-county** historical baseline of compatible measure semantics, geography, complete periods and methodology era. Require a configured lookback, minimum count/evidence support, freshness, and material-change criterion. An interval/floor comparison is allowed only if the approved rule can prove its direction/materiality for all values consistent with the published bounds; an unbounded floor generally cannot prove an increase against another floor. Missing county-years are unknown, not zero. Rate comparison additionally requires a valid same-county/year denominator; count-only comparison must be explicitly labeled as reported counts, not incidence. Return `EMERGING_HUMAN_SIGNAL` with current/baseline evidence references and bounded explanation only if every gate passes; otherwise `NO_COMPARABLE_HISTORY`, `METHODOLOGY_ERA_UNSUPPORTED`, `SOURCE_SEMANTICS_UNKNOWN` or another exact abstention reason. Unapproved configuration fails closed as a configuration error, not a scientific finding. No national cross-sectional score or percentage threshold is approved.

**Emerging vector/pathogen contract:** inputs must be time-varying **county-native** observations for the same vector taxon or pathogen target and source/method stratum, with observation windows, design, effort/test denominators where applicable, value/evidence state, source revision and provenance. Compare only like constructs and compatible periods after an approved source-specific minimum effort, freshness and material-change rule. Return `EMERGING_VECTOR_PATHOGEN_SIGNAL` with both periods and method/effort evidence only when those gates pass. Current/cumulative county status, isolated site events and passive submissions do not form an annual county prevalence series. Transition from unknown/no record to positive is newly documented evidence, not biological emergence. The precise missing capability is a governed time-varying county-native source plus approved comparison semantics; Data #429 and API #88 address evidence-state propagation, but do not themselves manufacture that source. Keep disabled until an eligible source is established.

**Discordance contract:** inputs are two otherwise independently interpretable observed human and county-native vector/pathogen families with exact source/product/version, geography/grain, observation intervals, method and era, sampling design/effort, value/evidence state and provenance. Require a reviewed allowed source pair, compatible geography or explicitly approved bounded mismatch, aligned periods or governed alignment, sufficient rule-specific completeness in **both** families, and configured material difference criterion. Return `HUMAN_VECTOR_DISCORDANCE` only for a supported apparent difference, with both evidence references and review-only wording. A human observation is residence-based, not proven exposure; local travel/exposure information is unavailable. Positive vector evidence paired with _missing_ human data is not a discordance candidate; it may be an independently qualified candidate from another enabled rule plus a human data gap. Human positive paired with `No records` vector status is never proof of vector absence. Passive versus systematic collection, site versus county, cumulative versus annual, sparse effort and reporting changes fail the comparison gate unless an exact approved method resolves them. Abstain with `INCOMPATIBLE_PERIODS`, `INSUFFICIENT_SAMPLING`, `COMPARABILITY_UNKNOWN` or source-specific reason. No expected-case formula, underreporting, causality, outbreak, or local-transmission statement follows.

**Review stages — approved v1 policy:** do **not** automatically assign `Continue routine review`, `Monitor the pattern`, `Verify with local information`, or `Prioritize targeted follow-up`. Return why surfaced, contributing observations, completeness, caveats, gaps, abstention/unsupported state and a bounded `suggested_next_check` where warranted (for example inspect source revision, local exposure information, or sampling design). Web #269 validates terminology and stage interpretation for later versions. No stage mapping blocks #249, API #93 or Web #411; none of these labels is an ordinal disease-risk category.

Invalid or unapproved configuration is an API configuration error/fail-closed condition, never an epidemiologic finding. Preserve upstream source reason codes alongside these review codes. `SAMPLED_NOT_DETECTED` is an evidence state, never a candidate reason; it requires a documented completed sample/test and valid denominator in its native stratum.

## Product Owner / scientific decisions before candidate activation

1. **Human baseline and change:** Approve source/series, same-era lookback, count/denominator eligibility, materiality comparator/value and freshness. Recommended default: fail closed with human emerging disabled until a governed comparable series and backtest exist. Alternative: a source-backed status transition rule, if the source actually defines one. Risk: a one-year floor or reporting artifact looks like emergence. **Blocks human emerging candidates, not the contract.**
2. **Vector/pathogen change:** Approve whether any county-native temporal source, status transition and minimum effort support an emerging rule. Recommended default: disabled; show current positive status as evidence only. Alternative: later source-specific rule after Data #429/API #88 projection and validation. Risk: cumulative or passive reports masquerade as annual change. **Blocks vector emerging candidates only.**
3. **Discordance comparator:** Approve eligible human/vector source pair, period alignment, adequate sampling, and material difference criterion. Recommended default: disabled until residence/exposure, sampling design and reporting-era limitations are addressed in source-backed fixtures. Alternative: labeled descriptive side-by-side evidence without a discordance candidate. Risk: falsely implying underreporting or local transmission. **Blocks discordance candidates only.** Automatic review-stage mapping is **decided**: none in bounded v1. Web #269 may propose a later validated mapping.

Web #455 owns the later **post-deployment** review of rule enablement, evidence-family participation, source/version allowlists, freshness, comparison windows, minimum support, materiality, explanations and possible stage assignment. It can approve changed settings as a versioned methodology/configuration update without redesigning API #93. Its scheduled meeting is not a prerequisite to accepting this initial specification or delivering API #93 and Web #411.
